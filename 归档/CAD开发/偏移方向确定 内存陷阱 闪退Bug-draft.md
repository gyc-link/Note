## 实战经验与踩坑

### 偏移方向怎么确定？

**背景**：已知一条轮廓线（可能开放）和用户点选位置，要对所有曲线做偏移，决定每条曲线 `offsetDist` 的正负号。

**为什么不用 CW/CCW？** 顺时针只在闭合回路中有定义，开放曲线不适用。

**思路**：以第一条曲线为判断基准。

1. 限定用户点选位置在第一条曲线的两端点之间
2. 偏移第一条曲线，返回两条偏移结果
3. 比较用户点距两条偏移曲线的距离 → 选出第一条曲线的正确偏移方向和符号
4. 其余曲线：与第一条曲线比走向 → 一致则同符号，相反则反符号

```
第一条曲线 = 基准，用户点在哪侧 → 确定符号
其余曲线 = 跟基准比走向 → 一致则同号，相反则反号
```

**优化思路**：以离点最近的曲线为判断基准。

```
离点最近的曲线 = 基准，用户点在哪侧 → 确定符号
其余曲线 = 跟基准比走向 → 一致则同号，相反则反号
```

### OffsetCurve3d 内存与拟合陷阱

#### 指针寄生关系

`new OffsetCurve3d(curve3d, ...)` 在 C++ 底层**不复制数据**，只存一个指向 `baseCurve` 的指针。当别人找它要坐标时，临时在 `baseCurve` 基础上做数学偏移。

**关键后果**：如果 `curve3d` 被 dispose，即显式抹除这块内存，但 `offset` 的指针仍指向它。此时想访问 offset 的相关数据 → 访问已脱离控制的 C++ 内存 → **Access Violation 闪退**。

```csharp
// 父亲在最外层
using (var line3d = line.GetGeCurve())
{
    // 儿子嵌套在里面
    using (var offsetLine = new OffsetCurve3d(line3d, Vector3d.ZAxis, 10))
    {
        // 读写安全
        Point3d pt = offsetLine.StartPoint;
    }
    // 1. offsetLine 自动安全死亡
} 
// 2. line3d 自动安全死亡
```

#### CreateFromGeCurve 的拟合退化

`Curve.CreateFromGeCurve(offset)` 内部流程：

1. 转换引擎发现偏移曲线的数学模型太复杂（没有简单解析方程）
2. 底层调用**逼近拟合算法**，强行算出 `CubicSpline3d`（分段三次样条几何体）
3. 包装进数据库 `Spline` 实体

**退化的结果**：新 `Spline` 的 `NumFitPoints`（拟合点数量）= 0，所有形状信息被打散成海量控制点和节点矢量。表面是三次样条，内部是纯 NURBS。

**引发的两个问题**：
1. 用最简构造函数去读拟合点 → 读到 0 个 → 分母为 0 错误
2. 拿去求交、Split → 控制点数据冗余且带浮点误差 → C++ 迭代算法陷入死循环或内存溢出 → 闪退

### 曲线交点注意事项

`CurveCurveIntersector3d` 返回的参数值取决于参与求交的具体曲线对象类型和内部参数化方式。
- `Polyline`（哪怕只有一段直线）≠ `Line`
- AutoCAD 可能对 `Arc` 使用不同参数映射
- **交点位置相同，但返回参数值可能不同**
- **判断准则：参数值不可靠比较，交点坐标才可靠。**

| 类型 | 英文 | 含义 |
|---|---|---|
| 横截相交 | Transversal Intersection | 两条线交叉穿过彼此 |
| 切向相交 | Tangential Intersection | 两条线在交点处相切，方向一致 |

## 闪退 Bug 记录

**Bug 1：二次误切导致零长度碎片**

- 初次裁剪：线 A 与线 B 相交 → 成功裁剪 → 几何物理连通（端点精准重合）
- 再次遍历：逻辑条件过简 → 误认为它们再次相交
- 二次误切：在重合的端点上切刀 → 分割出长度为 0 的碎片
- 崩溃：保留了 0 长度无效实体 → 非托管内存越界 → CAD 闪退

**Bug 2：复合实体求交点参数异常**

多段线跟圆弧求交点时，交点在圆弧上的参数值不正常。两条样条曲线求交点时有问题，设置 `global` 后解决。
