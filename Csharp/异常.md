## 引入

调用一个方法时，你期望它正常执行、返回结果。但现实里总有意料之外的情况——文件不存在、网络断了、参数是 null、数据库连接超时。这些**运行时错误**如果不管，程序直接崩溃，用户看到一坨报错信息。

异常机制做的事：**把"出错了"这个信号，从出错的地方传到一个能处理它的地方，中间该清理的资源自动清理。**

## 什么是异常

>[!help]- 什么是异常
>异常是程序在**运行时**发生的错误——违反了系统约束或应用程序约束。正常操作下异常**不会发生**。
>
>常见例子：除以 0、往只读文件写数据、访问 null 对象的成员。
>
>而错误是程序员不可预见的。

>[!important] 关键
>如果程序没有提供处理异常的代码，系统会挂起（崩溃/终止）该程序。

异常处理程序的三个核心目标：

1. **尝试恢复**：少数情况下能修复错误，让程序继续运行
2. **记录 + 清理**：记日志、释放数据库连接、关闭文件流
3. **友好提示**：给用户看能看懂的错误信息，而不是底层堆栈

## try 语句

try 语句用来圈出"受保护"的代码段。它由三个部分组成：

| 部分 | 必须？ | 作用 |
|---|---|---|
| `try` 块 | **必须** | 包含受保护的代码 |
| `catch` 子句 | 可选（与 finally 至少有一个） | 处理 try 块中抛出的异常 |
| `finally` 块 | 可选（与 catch 至少有一个） | 无论有没有异常都执行的清理代码 |

>[!NOTE] 结构规则
>- `try` 不能单独存在
>- `catch` 和 `finally` 必须至少有一个
>- 如果都有，顺序必须是：`try` → `catch` → `finally`

## 异常类

### 继承层次

所有异常类最终都派生自 `System.Exception`：

```
System.Object
  └── System.Exception
        ├── SystemException          ← 系统预定义异常的基类
        │     ├── IndexOutOfRangeException
        │     ├── NullReferenceException
        │     └── IOException
        └── ApplicationException     ← 用户自定义异常的基类
```

>[!note] 可以自定义异常类，继承自System.Exception

### 异常对象的属性

当异常发生时，CLR 创建该类型的异常对象。你可以通过它的属性获取错误信息：

| 属性 | 类型 | 作用 |
|---|---|---|
| `Message` | `string` | 解释异常原因的错误消息 |
| `StackTrace` | `string` | 异常在何处发生的堆栈追踪 |
| `InnerException` | `Exception` | 如果当前异常是由另一个异常引起的，这里引用前一个异常 |
| `Source` | `string` | 抛出异常的程序集名称 |

> `catch(Exception ex)` 时最常用的是 `ex.Message`。

## catch 子句的四种形式

| 形式 | 语法 | 能访问异常对象？ | 适用场景 |
|---|---|---|---|
| 一般 catch | `catch { }` | 不能 | 兜底，不推荐 |
| 特定 catch | `catch (ExceptionType) { }` | 不能 | 只关心异常类型，不关心细节 |
| 带对象的特定 catch | `catch (ExceptionType ex) { }` | 能 | **最常用**——需要读 `ex.Message` |
| 带过滤器的 catch | `catch (ExceptionType ex) when (条件) { }` | 能 | 同一个异常类型，按条件分流处理 |

### 一般 catch（不推荐）

```csharp
catch
{
    // 匹配任何异常，但无法访问异常对象
}
```

>[!warning] 不鼓励使用
>它会隐藏错误，让程序在未知状态下继续运行。应尽可能用特定 catch。

### 带对象的特定 catch（最常用）

```csharp
catch (NullReferenceException ex)
{
    Console.WriteLine(ex.Message);
}
```

异常变量 `ex` 在 catch 块内相当于局部变量，引用异常对象。

### 异常过滤器（C# 6.0）

同一个异常类型，按条件分流给不同的处理程序：

```csharp
try
{
    // 执行某个 Web 请求
}
catch (HttpRequestException e) when (e.Message.Contains("307"))
{
    // 处理 307 重定向
}
catch (HttpRequestException e) when (e.Message.Contains("301"))
{
    // 处理 301 重定向
}
```

>[!NOTE] 匹配规则
>只执行**第一个**匹配成功的子句。即使有多个子句都满足条件也是一样。

>[!warning] when 的约束
>- 必须返回 `bool`
>- 不能是异步的（不能用 `await`）
>- 不应该做耗时操作
>- 谓词表达式内部发生的任何异常**都会被忽略**（这让调试变难，但保护了原始错误信息）

## catch 子句的排序规则

一个 `try` 后面可以有多个 `catch`。系统**从上到下**依次匹配，第一个匹配的执行。

```
try 块
 └── catch 子句段（按顺序匹配）
       ├── NullReferenceException   ← 最具体，排第一
       ├── Exception                ← 较通用，排后面
       └── catch { }                ← 无参数，必须最后
```

>[!important] 排序规则
>1. **由特殊到一般**：最特定的异常类型排第一，最通用的排最后。否则编译器报错。
>2. **一般 catch 垫底**：无参数的 `catch { }` 必须是最后一个。

## finally 块

>[!important] finally 一定会执行
>只要控制流进入了 `try` 语句，`finally` **始终会被执行**——无论有没有异常，无论 try 或 catch 里有没有 `return`。

两种控制流：

- **无异常**：`try` → 跳过所有 catch → `finally`
- **有异常**：`try` → 匹配的 catch → `finally`

```csharp
try
{
    // 即使这里有 return，下面的 finally 也会先执行
    return result;
}
finally
{
    // 清理代码：关闭文件、释放连接……
}
```

## 异常冒泡与栈展开

如果当前方法没有匹配的 catch，异常会沿着**调用栈向上冒泡**：

```
Method1() 调用了 Method2()
Method2() 内部抛出了异常
```

1. 系统先看 `Method2()` 有没有匹配的 catch
2. 如果没有 → 沿着调用栈找到 `Method1()`
3. 如果 `Method1()` 有匹配的 catch → **栈展开**：
   - 回到栈顶 `Method2()`
   - 执行 `Method2()` 的 `finally`
   - 弹出 `Method2()`
   - 回到 `Method1()`，执行匹配的 catch → 执行 `Method1()` 的 `finally`
4. 如果 `Method1()` 也没有 → 继续向上找，直到找到为止。最终找不到，程序崩溃。

## throw：抛出异常

### throw 语句

```csharp
throw new ArgumentNullException("参数不能为 null");
```

也可以在 catch 内部**不带异常对象**使用 `throw`——重新抛出当前异常，保留原始堆栈信息。

### throw 表达式（C# 7.0）

`throw` 可以作为**表达式**使用，放在以前只能写表达式的位置：

配合 `??`：
```csharp
set => mSecurityCode = value ?? throw new ArgumentNullException("Security Code may not be null");
```

配合 `?:`：
```csharp
string secretCode = safe
    ? SecretCode
    : throw new Exception("Not safe to get code.");
```
