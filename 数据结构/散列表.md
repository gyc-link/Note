## 引入

如果现在有一个菜单，用数组表示

`menu = [[“A”,1][“B”,2][“C”,3][“D”,4]]`

如果要查找某种食物的价格，数组无序，则依次访问数组中的每个元素，查看菜名是否对应，对应了再获得价格。这个过程往往为N步。如果是有序数组，则只需要logN步就能查找出来。

>[!important] 关键
>怎么做到，只要知道了食物的名字，一步就能获得这个食物的价格，这就是散列表要解决的事情。

## 基础概念

>[!help]- 什么是散列表
>散列表是一种通过**散列函数将关键字映射到数组下标**，从而实现快速存储、查找、删除对应值的数据结构，核心是”键值对”映射。

>[!INFO]
>散列表本质是**数组+散列函+冲突解决策略**的结合体，数组是存储载体，散列函数是定位核心，冲突解决是保障正常运行的关键。

## 散列函数

### 定义

散列函数，接收的key不管是什么形式的，输出的结果是**数组的下标**。且保证了每次对同一个key做散列计算时，得到的数组下标是确定的。

>[!warning]- 注意
>- 散列函数也要做到**运算速度极快**，如果散列函数本身就很复杂，计算过程就超过了O1复杂度，那就不是散列函数
>- 散列函数映射出的数组下标是**分布均匀的**，避免算出的结果都落在某些特定的区域里。

### 常见的散列函数

在实际应用中，关键字类型可能为数字、字符串、浮点数、大整数，甚至多种类型的组合。<span style="color:red;">通常会先将各种类型的关键字转换为整数</span>，再通过哈希函数映射到哈希表中。

针对整数类型关键字，常见的哈希函数设计方法包括：直接定址法、除留余数法、平方取中法、基数转换法、数字分析法、折叠法、随机数法、乘积法、点积法等。

1. 直接定址法 简单的线性映射
2. 除留余数法
	- 取key的模函数，index  = key MOD tableSize ，index始终保持在0到size-1之间。

### 散列函数在C# 的设计

散列表工作的数学前提是：**先靠哈希码定位桶，再靠相等判定在桶内精确匹配**。这两个步骤必须一致，否则散列表行为不可预测。

因此 C# 在 `object` 上同时放了两个虚方法，并要求一条铁律：

>[!note] 规定
> 1、如果 a和b相同，则 a、b的哈希码必然相同
> 2、哈希码不相同，则a和b必然不同
> 3、哈希码相同，对象可以不同——这就是散列表的**冲突**。
> 注意如果引入浮点数误差，往往没有传递性，即a=b，b=c，那么a和c不一定相等，这时候怎么处理。

#### 工程的三层控制：从默认到完全自定义

原理不管"散列函数谁来写"，工程要管。C# 给了三层递进的控制权：

**第一层：object 默认实现**

>[!help]- 引用类型与值类型在两个函数上的区别
>- `GetHashCode()`：引用类型基于对象引用标识生成哈希码，值类型基于所有字段的值生成。
>- `Equals()`：引用类型比是否同一引用，值类型逐字段比较。

因此任何对象都能直接当 `Dictionary` 的键，零配置。

**第二层：override 重写——类型自己定义散列方式**

当默认不对时，重写两个方法：

>[!example]
比如两个 `Student` 对象只要学号相同就算同一个人

```csharp
public class Student
{
    public int Id { get; set; }
    public string Name { get; set; }

    public override int GetHashCode() => Id.GetHashCode();

    public override bool Equals(object obj)
        => obj is Student other && this.Id == other.Id;
}
```

>[!warning] 注意
>重写一个就必须重写另一个。

**第三层：IEqualityComparer\<T\>**

重写只能定义一种比较方式。现实里同一个 `string`，有时区分大小写有时不区分。况且 `string` 是 `sealed`，根本不能重写。

`IEqualityComparer<T>` 把散列函数和相等判断从类型内部抽到外部：

```csharp
public interface IEqualityComparer<T>
{
    int GetHashCode(T obj);
    bool Equals(T x, T y);
}
```

>[!info]- 适用场景
>第三方 sealed 类型改不了源码、同一类型在不同字典里需要不同键逻辑、任何需要临时切换比较策略的情况。

**三层总览：**

| 层级  | 机制                                  | 含义            |
| --- | ----------------------------------- | ------------- |
| 默认  | `object.GetHashCode()` / `Equals()` | 不写代码就能当键      |
| 重写  | `override` 两个虚方法                    | 这个类型天生就该这么比   |
| 外部  | `IEqualityComparer<T>`              | 在这个特定字典里换一种比法 |

## 冲突解决机制

### 什么是冲突

如果散列函数最后得到的结果没法避免两个不同的key值算出同一个数组下标，此时就发生了冲突。

冲突发生的越多，散列表效率越低。

>[!info]
>- 这两个不同key有人称为同义词。
>- 此外，冲突的发生还跟数据量与格子数的比值：**装填因子**有关。

### 如何减少冲突

见下一节[找到平衡](#找到平衡)]

### 怎么解决冲突

#### 1. 线性探测（开放寻址法）

冲突时往后找下一个空位，直到找到为止。（表尾的位置是表首）

>[!INFO]-  优缺点
优点：数组内存连续，CPU 缓存友好。
缺点：容易出现**一次聚集**——冲突的 key 会聚在一段连续区域，探测链越来越长。

示例：
线性探测构造散列表

![](../pic/Pasted%20image%2020260529160511.png)

>由于除数是11，如果没有冲突的情况下，11这个位置是不会被映射到的。

>ASL成功 = (1+1+2+1+2+1+4+4+7)/9
>ASL失败 =（3+2+1+1+3+2+1+**8+7+6+5**）/11

⚙️ 基础配置
待存元素数量：9 个
数组容量 (Size)：12
装填因子 (Load Factor)：0.75
散列函数 (Hash Function)：H(key) = key(mod 11)
高频冲突源：计算结果为 7 的键共有 5 个（29、18、40、8、51）

查找场景一：

```
Get(8):
  1. 计算哈希值：H(8) = 8 % 11 = 7
  2. 探测位置 7 ：存储的是 29 ❌ (Key不匹配，发生冲突)
  3. 探测位置 8 ：存储的是 18 ❌ (Key不匹配，发生冲突)
  4. 探测位置 9 ：存储的是 20 ❌ (Key不匹配，发生冲突)
  5. 探测位置 10：存储的是 40 ❌ (Key不匹配，发生冲突)
  6. 探测位置 11：存储的是 8  ✅ (Key匹配成功)
  
  结果：查找成功，返回数据。
```

查找场景二：

```
Get(48):
  1. 计算哈希值：H(48) = 48 % 11 = 4
  2. 探测位置 4 ：存储的是其他元素/或不匹配 ❌
  3. 依次向下探测下一个位置...
  4. 探测到位置 X ：遇到 Empty（空位置） 🛑
  
  结果：探测链断开，说明数组中绝对没有 Key 为 48 的元素，查找失败。
```

查找场景三：

```
Get(8):
  1. 计算哈希值：H(8) = 8 % 11 = 7
  2. 探测位置 7 ：存储的是 29      ❌ (Key不匹配，继续)
  3. 探测位置 8 ：存储的是 18      ❌ (Key不匹配，继续)
  4. 探测位置 9 ：状态为 [Deleted] ⚠️ (墓碑：知晓此处曾有元素，跳过并强行继续探测！)
  5. 探测位置 10：存储的是 8       ✅ (Key匹配成功)
  
  结果：成功越过被删除的空缺，查找成功。
```


>[!definition]
>ASL(Average Serach Length) 平均查找长度
>
>查找成功的ASL  
>在散列表中，找到**已经存在**的元素，平均需要对比多少次。
>![](../pic/Pasted%20image%2020260529162353.png)
>
>查找失败的ASL    
>在散列表中，断定一个**不存在**的元素确实不存在，平均需要对比多少次。
>因为最后映射到的结果不会有11，所以位置11处不需要参与计算。从0到10计算查找不在表里的其他关键字需要几次，最后除以11就是查找失败的ASL
>![](../pic/Pasted%20image%2020260529162407.png)


#### 2. 链式法（拉链法）

数组每个槽位不再存一个元素，而是存一条链表（或红黑树）。冲突的元素挂在同一个槽的链表上。（一般使用头插法）

```
  [0] -> (“1001”,”李四”) -> (“1012”,”张三”)
  [1] -> (“1002”,”王五”)
  [2] -> Empty
```

>[!INFO]-  优缺点
优点：删除简单，不需要墓碑；负载因子可以 > 1。
缺点：链表节点分散在堆上，CPU 缓存不友好；极端情况退化为 O(n) 遍历。

#### 槽位状态机 —— 每个格子的三种身份

散列表的每个槽位不只是”有东西”或”没东西”。删除操作引入了一个关键的状态——墓碑。

>如果直接设为Empty，则会截断后续的（查找、增加、删除）探测。

```
            Add(id,name)
 Empty -------------------> Occupied
   ^                            |
   |                            |
   |      Remove(id)            |
   +---- Deleted <--------------+
            |         ^
            |         |
            +---- Add(id,name) --+  (墓碑可被新数据复用)
```

| 状态       | 含义            | Get 遇到它      | Add 遇到它              | Remove 遇到它    |
| -------- | ------------- | ------------ | -------------------- | ------------- |
| Empty    | 从没放过数据        | 停止探测，返回 null | 写入                   | 停止，key 不存在    |
| Occupied | 有数据住着         | 比对 key，匹配就返回 | 比对 key，相同就更新，不同就继续探测 | 匹配就标为 Deleted |
| Deleted  | 数据被删了，但探测链不能断 | 跳过，继续探测      | 记下位置（优先复用），继续探测      | 跳过，继续探测       |

>[!WARNING] 为什么 Deleted ≠ Empty？ 
>这是散列表最容易踩的坑。假设学号 1001 和 1012 都对 11 取模得 0，1012 被挤到位置 1。此时删了 1001——如果把位置 0 标回 Empty，下次 `Get(1012)` 算得 hash=0，一看位置 0 是 Empty，直接 return null，位置 1 的 1012 永远找不到了。所以删过的格子必须留一个墓碑，告诉探测”别停，后面可能还有”。

>[!NOTE] 笔记
>探测链不能断

## 找到平衡

### 什么是平衡

其实平衡就是要尽可能的**减少冲突。**

一个散列表要存多少数据、有多少可用的格子，用什么样的散列函数，才能保证既能避免冲突，又能节约空间？

举个例子：如果只存10个数据，通过散列函数计算得到的数组下标最大是1000，那么就要用1001个格子，剩下的991个格子就是巨大的空间浪费。

### 解决办法


> [!QUESTION]- 怎么找到平衡
> 1. 量化平衡： **装填因子**
> 	- 设计合理的装填因子，保证空间不浪费的情况下，冲突发生的可能性也小。
> 	- 现在成熟的思想是：每增加7个元素，就增加10个格子，因此理想的负载因子是0.7
> 2. 散列函数要做到均匀。
> 	- 有理论证明除留余数法中使用小于表长的最大质数作为除数，可以减少冲突。


### 自定义学号-学生名散列表

使用线性探测解决冲突，散列函数选择除留余数法。
初始容量设置为11，装填因子设置为0.7，实现自动扩容和缩容

由于线性探测是冲突后找下一个空位，直到找到为止，如果到表尾还没找到，需要接着从表首开始。所以这是一个线性探测是一个环状的探测。

设置循环，从i= hash 依次探测一圈，循环内部设置退出条件。
```csharp
for (int i = hash; ; i = (i + 1) % size){}
```

添加或者更新学号-姓名映射

1、更新映射关系
```csharp
if (states[i] == SlotState.Occupied && value[i, 0] == id)
{
    value[i, 1] = name;
    return;
}
```

2、添加映射关系

记录下探测过程中碰到的第一个墓碑。后续遇到空位，优先复用路径上的墓碑
```csharp
firstDeleted = -1
if (states[i] == SlotState.Deleted && firstDeleted < 0)
{
    firstDeleted = i; 
}
    
if (states[i] == SlotState.Empty)
{
    int target = firstDeleted >= 0 ? firstDeleted : i;
    value[target, 0] = id;
    value[target, 1] = name;
    states[target] = SlotState.Occupied;
    count++;
    return;
}
```

3、查找

如果遇到空位，说明key不存在
```csharp
if (states[i] == SlotState.Empty) return null
```

找到key的情况
```csharp
if (states[i] == SlotState.Occupied && value[i, 0] == id)
	return value[i,1]
```

当转了一圈没找到，退出循环，返回null

散列表的装填因子是什么？理想值是多少？该怎么扩容？
- 装填因子 = ==1;;数据量与格子数的比值==。
- 作用：量化冲突概率。装填因子越接近1，闭散列中冲突越容易发生。成熟实践是==1;;每增7个元素扩10个格子，理想装填因子 0.7==。
- 扩容方式：不是把老表数据一一对应拷贝到新表，而是==1;;逐一重新计算老表每个数据的哈希值，放入新表==。为什么要这么做？因为==1;;新表容量变了，除留余数法的除数变了，旧下标在新表里几乎全失效==。并且这样新表是==1;;干净的，不存在老表的墓碑==。
