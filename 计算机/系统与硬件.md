# 系统与硬件

## 系统 / 硬件操作

- 装系统：台式机按`delete`进 BIOS 改启动项；分区 ：装机时不要分区，系统盘左右会有间隔；UEFI 引导对应 GPT 分区，Legacy 对应 MBR 分区；可通过`shift+f10`执行`list disk`/`select disk`/`clean`/`convert gpt/mbr`命令；推荐微 PE，系统镜像从 MSDN / 微软官网下载。
- 显示器 / 主机：主板 / 显卡有 HDMI 接口，显卡多 DP 接口；主机接口对应 CPU 核显，BIOS 中开启核显支持多屏显示。

## x86 vs x64 架构

>[!question]- 32 位和 64 位的核心区别
>CPU 一次能处理的**地址宽度**。

- **32 位操作系统**：地址总线 32 位，最多寻址 2³² = **4 GB** 内存。插再多内存条，系统也用不上。
- **64 位操作系统**：理论寻址 2⁶⁴ = 16 EB（160 亿 GB）。实际实现中，当前 x86-64 CPU 只用 48 位做虚拟地址（256 TB），够用了。

> 所以老机器装 32 位系统、配 4 GB 以上内存是浪费——系统根本看不见多余的内存。

**二进制单位换算**（计算机里都是 1024 进制）：

| 简写 | 二进制单位 | 字节数 | 2 的幂 |
|------|-----------|--------|--------|
| **1 K** | 1 KiB | 1,024 | 2¹⁰ |
| **1 M** | 1 MiB | 1,048,576 | 2²⁰ |
| **1 G** | 1 GiB | 1,073,741,824 | 2³⁰ |
| **1 T** | 1 TiB | 1,099,511,627,776 | 2⁴⁰ |

> 硬盘厂商用十进制（1 K = 1000），所以买到的 1 TB 硬盘插电脑上显示约 931 GB——不是少了，是单位不同。

## 显示器

**光学三原色：RGB**。显示器上每个像素由红、绿、蓝三个子像素组成，调节各自亮度混合出所有颜色。这是**光的加法混合**——三色全亮 = 白色，全灭 = 黑色。

**原生分辨率**：显示器面板上实打实的发光点数量。4K 显示器物理上有 3840×2160 个像素点。系统里把分辨率调低后，GPU 画一张小画面，显示器硬件把它拉伸填满物理像素——所以会糊。**LCD 显示器只有在原生分辨率下才最清晰。**

>[!NOTE]- **屏幕尺寸**：
>常说的"多少英寸"指的是屏幕**对角线**的长度，不是长也不是宽。

**GPU 为什么能同时算那么多像素**：GPU 有几千个小核，每个核管屏幕上一小片格子。渲染时所有核同时开工，各算各的格子颜色——这就是"并行计算"。CPU 核少但每个核很强（处理复杂逻辑），GPU 核多但每个核很简单（做大量重复计算）。

## 抗锯齿

显卡在渲染画面时，为了消除物体边缘的"锯齿"（即像素化带来的阶梯状线条），会对每个像素点进行多次采样和计算。抗锯齿开得越高，显卡为了消除锯齿，在单位时间内需要处理的有效像素样本越多。

aliasing `/ˈeɪliəsɪŋ/`
多重采样抗锯齿（MSAA，Multi-Sampling Anti-Aliasing）：它只针对物体的边缘像素进行倍增采样。

如果开到 MSAA x 8，意味着显卡会对边缘像素进行 8 次 子像素采样，然后混合计算出最终的颜色。在这种情况下，并不是所有像素都计算8倍。屏幕上的非边缘区域（如大面积的天空或墙壁）依然只计算1次。但即便如此，当画面复杂时，显卡需要实时判断哪些是边缘，并对边缘进行高倍采样，计算量依然会大幅增加。

超级采样抗锯齿（SSAA，Super-Sampling Anti-Aliasing）
以高于目标分辨率的画面渲染，再降采样到目标分辨率。效果最好但性能开销最大。

时域抗锯齿（TAA，Temporal Anti-Aliasing） 和 深度学习超级采样（DLSS，Deep Learning Super Sampling）/ FSR（FidelityFX Super Resolution）
- TAA：利用上一帧的画面信息来辅助当前帧的抗锯齿，性能开销小，但可能导致运动模糊/拖影。
- DLSS/FSR：通过AI/算法将低分辨率画面重建为高分辨率，兼具抗锯齿和性能提升。

## CPU 缓存与数据结构性能

**数组遍历为什么比链表快？** 

答案在 CPU 缓存。

```
【内存】: [ 数组0 ][ 数组1 ][ 数组2 ][ 数组3 ][ 数组4 ][ 数组5 ]
              │        │        │        │
            ┌─┴────────┴────────┴────────┴─┐
            │  CPU 预读机制：打包一并带走    │
            └──────────────┬───────────────┘
                           ▼
【CPU 缓存】: [ 数组0 ][ 数组1 ][ 数组2 ][ 数组3 ]  ← 极速读取！
                           │
                           ▼
                    【 CPU 核心 】

结果：只有访问数组0 可能发生一次 Cache Miss，接下来的 1、2、3 全部 Cache Hit
```

```
【内存】: [ 节点1 (去A区) ] ...... [ 节点2 (去B区) ] ...... [ 节点3 ]
                │                          ▲
                └──────────────────────────┘ (顺着指针寻找)

            ┌──────────────────────────────┐
            │ CPU 预读：只能打包节点1周围的   │
            │ 无用垃圾数据，根本找不到节点2    │
            └──────────────┬───────────────┘
                           ▼
【CPU 缓存】: [ 节点1 ][ 内存邻居甲 ][ 内存邻居乙 ] ← 没能提前加载节点2！
                           │
                           ▼
                    【 CPU 核心 】 ──> 找不到节点2！触发 Cache Miss！
                                       被迫再次调头去主存搜寻...
```

每访问一个节点就要顺着指针去内存的新地方现找。上次预读进 Cache 的数据全部浪费，每次访问大概率伴随 Cache Miss。

> 核心原因：数组元素在内存中是**连续存放**的，CPU 一次预读能拉一批进缓存。链表节点**散落在内存各处**，指针指向哪就得跳到哪，CPU 的预读机制完全帮不上忙。
